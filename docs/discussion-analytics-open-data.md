# 💡 提案：`/analysis` を「日曜市の一次記録を公開する場所」に作り直す

## 背景：いまの `/analysis` は自分たちのアクセス解析を見せているだけ

現状の「日曜市をデータで見る」（`app/analysis/page.tsx`）が出しているのは 2 つだけです。

- **カテゴリ別出店比率**：`vendors.category_id` × `categories.name` の円グラフ（今この瞬間のスナップショット）
- **Web 来訪者数**：`web_visitor_stats` の日次／週次／月次／年次

このうち後者は **nicchyo というサービスの利用状況**であって、日曜市そのもののデータではありません。ページ内に「※この数値は現地来訪者数ではなく、Web来訪者数です」と注記があるのはよいのですが、裏を返せば「日曜市を見に来た人にとって使い道のない数字が、ページで一番大きく表示されている」状態です。

第三者（行政・研究者・報道・他地域のマーケット運営）から見ると、いまのページは **引用できるものが何もありません**。数字の定義がなく、機械可読な形で落とせず、ライセンスもなく、いつ時点のものか分からないからです。

一方で、リポジトリを棚卸しすると **nicchyo にしか存在しない一次データが既にかなりの量ある**ことが分かります。作り込むべきなのは可視化の見栄えではなく、その一次データを「他人が使える形にして出す」ところだと考えます。

---

## この提案の前提：読み手は 3 人いる

| 読み手 | 知りたいこと | いま満たせているか |
|---|---|---|
| **来訪者** | 今週やってる？ 何が旬？ どのくらいの規模？ | △（規模感だけ） |
| **第三者（行政・研究・報道・他地域）** | 引用できる数字と、その取り方 | ✗ |
| **支援を検討する人（協賛・寄付）** | このプロジェクトは何を残しているのか | ✗ |

3 人目は 2 人目の副産物です。**「引用できる記録を残している」ことが証明できれば、支援の理由は説明不要になります。**逆に、寄付を訴えるためのグラフを先に作ると、いちばん説得力のない構成になります。だからこの提案では 2 人目を主対象に置きます。

---

## 1. nicchyo にしかない一次データの棚卸し

いま DB にある／作れるもののうち、**他のどこも持っていない**ものを価値順に並べます。

### ★★★ 開催実績台帳（`market_days`）

「その日曜日に日曜市が開催されたか、荒天中止か、臨時休市か」を日付単位で持つテーブルです。`status` は `open / cancelled / special / closed`、RLS は全件公開、`updated_by` だけ列単位で伏せてあります。

これは**この提案の中で最も価値の高い資産**です。300 年以上続く街路市の開催／中止が、機械可読な形で残っている記録は他に存在しないと考えられます。しかも気象庁の高知地点の日降水量と結合するだけで、

- 「どのくらいの雨量で中止になるのか」
- 「中止率は年ごとに増えているのか（気候変動の地域影響）」
- 「中止の判断は年々早くなっているか」

が言えます。防災・気候・観光・地域経済のどの分野からも引用され得る種類のデータです。**1 年に 52 行しか増えませんが、続ける限り価値が複利で増える**という点で、他のどの指標とも性質が違います。

- 過去分（少なくとも直近数年）を新聞・高知市の記録から遡って入力する価値が非常に高い
- `note`（「雨天のため中止します」）は自由記述なので、公開時は `status` と日付のみを機械可読にし、`note` は表示用に留める

### ★★★ 出店構成の空間分布（`vendors` × `categories` × `location_assignments` × `market_locations`）

約 1.3km の街路に約 300 店という空間密度そのものが、都市計画・商業地理の観察対象です。`location_assignments` が `market_date` × `location_id` × `vendor_id` を持っているので、**「何丁目に、何のカテゴリの店が、何軒あるか」を日付付きで出せます。**

- カテゴリ × 丁目のマトリクス（今すぐ出せる）
- その推移（**今から貯めないと永久に出せない** → 後述）

### ★★ 旬カレンダー（`products` × `product_seasons` × `seasons`）

「高知の路上市場に、実際に何月に何が並ぶか」。農林水産統計の出荷データとは別物で、**小規模生産者が実際に持ってくるものの記録**です。食文化・農業・観光のいずれからも一次資料になります。来訪者にとっても実用的で、層をまたいで効く数少ない指標です。

### ★★ 生活インフラとバリアフリー（`map_landmarks`）

トイレ・休憩場所・電停・建物を `category` / `tags` / `latitude` / `longitude` / `verified` / `open_from` / `open_until` で持っています。**`verified` フラグがあるのが決定的に重要**で、「位置を実地確認済みかどうか」を区別して出せるデータセットは珍しい。

「日曜市開催中に使えるトイレと休憩場所の位置」は、車椅子利用者・高齢者・子連れの回遊可能性に直結します。OpenStreetMap への還元も検討できます。

### ★★ 会場内の徒歩実測（`guide_events`）

`distance_meters` / `walk_minutes` / `spot_key` / `origin_type` を持っています。個票は出せませんが、集計すれば **「会場のどのあたりから、最寄りのトイレまで何分か」の実測分布**になります。「6 丁目側はトイレまで平均 N 分」といった、施設配置の妥当性を数字で言える材料は行政にとって希少です。

### ★ 来訪者の関心（`ai_consult_logs.intent_category` / `keywords`、`product_search_logs.keyword`）

「初めて来た人が何に困り、何を探すか」の記録。観光行政が最も欲しがる類の情報です。ただし **`question_text` は自由入力なので絶対に生では出しません**。`intent_category` と `keywords` の集計のみ、かつ後述の出現数しきい値を必ず通します。

### ★ 出店者の稼働（`vendors.closed_dates`、`shop_attendance_vendor`）

個店単位は出しませんが、集計すれば「季節ごとの出店率」「雨天時の出店率」になります。ただしカバレッジの偏りが最も大きい領域なので、母数の開示（後述）が必須です。

## 2. いちばん急ぐ話：時系列は今日から貯めないと永久に手に入らない

上の表で「今すぐ出せる」ものはすべて **現在時点のスナップショット**です。カテゴリ別出店比率も、旬カレンダーも、「今こうなっている」しか言えません。

しかし第三者にとって価値があるのはほぼ常に**推移**の方です。そして推移は、遡って作ることができません。

> **提案：`vendors` / `categories` / `products` / `market_days` の集計値を、月次で CSV に凍結してリポジトリにコミットする仕組みを、他の何よりも先に作る。**

GitHub Actions で月 1 回、集計 SQL の結果を `data/open/YYYY-MM/*.csv` として commit するだけで済みます。実装量は小さいのに、**5 年後にこのプロジェクトが持つ資産の大きさを決めるのはこれ**です。可視化は後からいくらでも作れますが、2026 年 9 月の出店構成は 2026 年 9 月にしか記録できません。

副次的な利点として、リポジトリにコミットされた CSV は Git 履歴が改変履歴そのものになるため、**「後から数字を書き換えていない」ことの証明**になります。引用可能性の観点でこれは大きい。

## 3. ページの構成：3 層に分ける

いまの `/analysis` は「グラフが 2 つ並んでいる」だけなので、読み手 3 人のどれにも刺さっていません。次の 3 層に分けることを提案します。

### 層 1「いま」— 来訪者向け

- 今週の開催ステータス（`market_days`）
- 出店数と、その内訳（カテゴリ・丁目）
- 今月の旬（`product_seasons`）

### 層 2「記録」— 第三者向け（ここが本体）

- **開催実績カレンダー**：年ごとの週次ヒートマップ（開催／中止／特別）＋ 年別の中止率
- **出店構成**：カテゴリ × 丁目のマトリクスと、その推移
- **旬カレンダー**：12 か月 × 品目の一覧
- **生活インフラ**：トイレ・休憩・電停の件数と、うち位置確認済みの件数
- 各セクションに **CSV / JSON のダウンロードリンク**を必ず置く

### 層 3「このデータについて」— 信頼の担保

- 各指標の定義・収集方法・母集団・欠測の扱い（データ定義書）
- カバレッジ率（後述）
- ライセンスと出典表記の書き方
- 更新日と版

**協賛・寄付の導線は層 3 の直後に置きます。**「この記録を続けるために」という文脈で読まれるのが、いちばん自然で、いちばん強いからです。層 1 の横に寄付ボタンを置くのは、来訪者にとってノイズにしかなりません。

---

## 4. 「第三者が引用できる」ための最低条件

グラフを綺麗にすることと、引用されることは別の話です。引用されるために要るのは次の 5 つで、どれも欠けると引用が止まります。

| 条件 | 具体 |
|---|---|
| **ライセンス** | CC BY 4.0 を推奨。出典表記の例文をページに書いておく（「出典：nicchyo（KochiDXClub）／CC BY 4.0」） |
| **機械可読** | 画面のグラフだけでは引用されない。**URL 固定の CSV / JSON が要る**。`/api/open-data/...` か静的ファイル |
| **データ定義書** | 各列が何で、どう数えたか。「出店数」が「登録店舗数」なのか「その日出ていた店の数」なのかで意味が全く違う |
| **版と永続性** | スナップショットに年月の版を付け、過去版も残す。引用先のリンクが切れないこと。将来的には Zenodo 連携で DOI も取れる |
| **更新の約束** | 「月次で更新」と書き、実際に更新する。止まった記録は引用されない |

このうち **データ定義書が実質的に一番効きます**。これがない数字は、どれだけ正確でも研究者は使えません。逆に定義さえ書いてあれば、多少粗いデータでも使ってもらえます。

## 5. 偏りと正確性：隠すのではなく、開示する

「偏りのない情報収集」を目指したいという話でしたが、**現実には偏りは必ず残ります**。nicchyo のデータには少なくとも次の偏りがあります。

| データ | 偏りの中身 |
|---|---|
| Web 来訪者数 | スマホを持ち、検索して調べる層に偏る。**日曜市来場者の代表標本ではない** |
| AI 相談のキーワード | 「言語化できた不安」だけが残る。言葉にできなかった層は丸ごと落ちる |
| 出店者の申告データ | 申告してくれる出店者（デジタルに前向きな層）に偏る。`docs/discussion-seasonal-tag.md` の 3 層のうち不信層はほぼ落ちる |
| おでかけサポートのログ | 機能を見つけて使った人だけ。困っていても使わなかった人は残らない |

ここで取るべき態度は「偏りをなくす」ではなく、**「偏りの大きさを数字で併記する」**です。具体的には次を提案します。

> **すべての指標の隣に、母数とカバレッジ率を出す。**
> 例：「主要商品を登録済みの店舗：128 / 300 店（42.7%）」
> 例：「この集計は nicchyo に登録のある 128 店を対象としており、日曜市全体の出店者を代表するものではありません」

データの穴を隠さないことは、信頼を損なうどころか **信頼の根拠になります**。行政や研究者がまず見るのはカバレッジ率で、そこが正直に書かれていないデータセットは、その時点で使われません。

さらに、**データ品質そのものを公開指標にする**ことも提案します。

- 店舗情報の最終更新からの経過日数の分布
- 営業時間・支払い方法・雨天時対応が登録済みの店舗の割合
- `map_landmarks` の `verified` 済み件数 / 全件

これは同時に、協賛・寄付の訴求材料としても正直で強い材料になります（「ここまで埋まっている／ここが埋まっていない、だから続ける必要がある」）。

## 6. 公開しないと決めておくこと

作り込む前に、**出さないもの**を先に決めておくべきです。

| 出さないもの | 理由 |
|---|---|
| **個店単位の閲覧数・人気度・ランキング** | 出店者の営業情報であり、序列化は現場の関係を壊す。`docs/CONCEPT.md` の「効率的に回る場ではない」という思想にも正面から反する |
| `ai_consult_logs.question_text` の生テキスト | 自由入力。個人が特定できる記述が混ざりうる |
| 出現数が少ないキーワード・カテゴリ | しきい値（例：5 件未満）を下回るものは `-` で伏せる。**k-匿名性の担保** |
| `visitor_key` を含む一切の粒度 | 既に `web_page_analytics` は 35 日で削除、`web_page_daily_summaries` に集約する設計になっている（`20260817215000`）。公開系は日次集計以下に降りない |
| 個店の休業実績（そのまま） | 「あの店は最近来ていない」が読み取れてしまう。集計値のみ |

なお、この 5 つのうち後半 3 つは、既に DB 側の設計（`purge_expired_personal_data`、日次サマリー化、列単位 GRANT）が同じ方向を向いています。**公開ページはその設計の延長線上に置けばよく、新しく個人情報を集める必要はありません。**これは「個人が特定されない範囲に限定する」という方針にとって好都合な出発点です。

## 7. 進め方（PR 分割案）

`CLAUDE.md` の方針どおり、1 PR = 1 目的で分けます。上ほど優先度が高い順です。

| # | 内容 | 目的 | 規模 |
|---|---|---|---|
| 1 | **月次スナップショットの自動コミット**（GitHub Actions + 集計 SQL → `data/open/`） | 時系列の蓄積を今日から始める | 小 |
| 2 | ページを 3 層構成に再編。層 1 に開催ステータス・出店数・カバレッジ率を出す。Web 来訪者数は層 2 へ降ろし、注記を強化 | 「サービスの数字」を主役から外す | 中 |
| 3 | 開催実績カレンダー（`market_days` の年次ヒートマップ＋中止率） | 最重要資産を可視化する | 中 |
| 4 | 層 3「このデータについて」＋ データ定義書 ＋ ライセンス表記 | 引用可能にする | 中 |
| 5 | CSV / JSON ダウンロード（URL 固定） | 引用可能にする | 中 |
| 6 | 旬カレンダー（12 か月 × 品目） | 来訪者と第三者の両方に効く | 中 |
| 7 | 出店構成マトリクス（カテゴリ × 丁目） | 空間データの公開 | 中 |
| 8 | 生活インフラ（トイレ・休憩・電停の件数と確認率） | バリアフリーの材料 | 小 |
| 9 | 協賛・寄付の導線を層 3 直後に設置 | 支援を求める | 小 |

`market_days` の過去分の遡り入力は、コードではなく運用の作業なので PR とは別に進める必要があります。**ただし優先度は #1 の次くらいに高い**と考えます。

## 8. 決めたいこと

1. **ライセンスは CC BY 4.0 でよいか。** 高知市との関係上、出典表記の主体を「nicchyo」にするか「KochiDXClub」にするか、市を併記するか。
2. **`market_days` の過去分をどこまで遡るか。** 遡れる情報源はあるか（高知市の記録・新聞・出店者の記憶）。
3. **公開の下限しきい値を何件にするか。** 提案は 5 件。
4. **月次スナップショットの粒度。** 月次でよいか、開催日（毎週日曜）単位まで持つか。`location_assignments` があるので週次も技術的には可能。
5. **カバレッジ率の分母をどう定義するか。** 「日曜市の全出店者数」の権威ある数字はあるか（市の許可店舗数など）。これが取れると、`vendors` の登録数との比が出せて、カバレッジの開示が一気に正確になる。

## 補足：この方向が「寄付・協賛のお願い」に効く理由

マップの提供は「便利なものを作った」という話です。これは価値がありますが、**代替可能に見えます**（誰かが別のマップを作ればよい、と思われる）。

一方、開催実績台帳・出店構成の時系列・旬の記録は、**続けている主体しか作れず、途切れたら二度と埋まりません**。「私たちが止めると、この記録が途切れます」は、支援を求める理由として最も強い形の一つです。

そしてその主張が成立するのは、記録が **他人に使える形で公開されているとき** だけです。だから層 2 と層 3 が本体で、寄付の導線はその後ろに置く、という構成を提案します。
