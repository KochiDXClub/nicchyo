# 店舗カテゴリ

表示名・一覧の正は Supabase の `categories`。店舗との対応は `vendors.category_id` で管理する。名前は識別子にしない。

- 共通型と名前の解決: `lib/categories/catalog.ts`
- 匿名で読める一覧の共有キャッシュ: `lib/categories/server.ts`
- クライアント共通の購読・IDによる選択状態: `lib/categories/CategoryContext.tsx`
- 色の定義: `lib/categories/presentation.ts`。旧map/configは互換再エクスポートのみ。

`presentation_key` は名前を変えても維持する色・絵・既定画像のキー。DBマイグレーション `20261103000000_category_presentation_key.sql` を適用する。既存の7系統を元の名前と登録済みのIDから初期化し、「食材→野菜・果物」も同じ見た目を引き継ぐ。新規の独自カテゴリには汎用の見た目を使用する。運営で名前を変更してもキーは変更しない。

管理APIの追加・変更・削除後はカテゴリと公開店舗のキャッシュを両方破棄する。同じブラウザのタブへは更新イベントを送り、ほかの端末も5分ごとの更新・フォーカス復帰で取得する。通信障害時は最後の正常な一覧を維持する。店舗キャッシュはIDで現在名へ補正し、開いているバナーも更新する。カテゴリに差があればrouter.refreshでServer ComponentのLP・店舗データも更新する。

LPのカテゴリリンクはIDを使う。既存の表示名と旧プリセット名のリンクも、DB一覧の現在名・presentation_keyを通して解決する。独自カテゴリは旧表示名の履歴を持たないため、改名後は共有済みの旧名称URLを解決できない。デモの絵・オフライン控えデータには固定の表示キーが残るが、実際の選択肢・店舗の表示名の正にはしない。

本番DBはこのPR作業では変更しない。マイグレーションを適用してから、管理画面で改名し、別タブのマップ・開いているショップ詳細・LP・検索・出店情報編集を確認する。
