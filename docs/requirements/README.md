# ロール別 機能要件ドキュメント

nicchyo の機能を **ロール（誰が使うか）** ごとに整理し、各機能の「要件」と「重要な要素」を **重要度付き** で記録する場所です。

| ロール | ドキュメント | 主な画面 |
|---|---|---|
| 来訪者（未ログイン含む `general_user`） | [visitor.md](./visitor.md) | `/map` `/search` `/consult` `/story` ほか |
| 出店者（`vendor`） | [vendor.md](./vendor.md) | `/my-shop` `/vendor/*` |
| 管理者（`admin`）・モデレーター（`moderator`） | [admin.md](./admin.md) | `/admin/*` `/moderator` |

## このドキュメントの位置づけ

| 知りたいこと | 正典 |
|---|---|
| **誰に・何を提供するか（要件・重要度）** | このディレクトリ |
| なぜ作るか・何を作らないか（企画） | [FEATURES.md](../FEATURES.md) / [CONCEPT.md](../CONCEPT.md) |
| どう実装されているか（マップ・相談まわり） | [map-spec.md](../map-spec.md) |
| 管理画面の項目 | `lib/admin/adminNav.ts`（単一情報源） |
| 出店者の画面の使い方 | `lib/vendor/helpGuide.ts`（単一情報源。#767 のマージで `lib/vendor/helpFaq.ts` に置き換わる予定。マージ時にここを直す） |

矛盾した場合は **「実装の事実」はコードと map-spec.md、「あるべき姿・優先度」はこのディレクトリ** を正とします。

## 重要度の基準

nicchyo の設計思想（FEATURES.md）は「初来訪者の不安を和らげ、体験を始められる状態をつくる」です。重要度はこの目的への寄与で決めます。

| 記号 | 意味 | 判断基準 | 壊れたときの扱い |
|---|---|---|---|
| **S** | 必須（コア） | これが無いとそのロールにとってサービスが成立しない | 即時対応。リリースを止める |
| **A** | 重要 | 無いと明確に困る。体験・運用の質を大きく左右する | 次のリリースまでに直す |
| **B** | 通常 | あると便利。無くても代替手段がある | 通常の優先度で対応 |
| **C** | 補助 | 付加価値・将来用。削っても目的は達成できる | 余力があれば対応 |

「重要な要素」欄は、**その機能の中で絶対に外してはいけない性質**（例: 登録不要・表示速度・誤公開の防止）を指します。リファクタや改修時のチェックリストとして使ってください。

## 状態の凡例

| 記号 | 意味 |
|---|---|
| ✅ | 実装済み |
| 🟡 | 一部実装 / 方針決定済みで移行中 |
| ⬜ | 未実装（要件のみ） |
| ❓ | コードから確認できていない（要確認） |

## 運用ルール（更新方法）

1. **機能を追加・変更・廃止する PR では、該当ロールのドキュメントも同じ PR で更新する。** PR テンプレートに「要件ドキュメント更新」のチェック欄を置く。
2. 重要度の **変更** は、PR 説明に理由を書く（GitHub 上で履歴とレビューが残る）。
3. 実装した機能の状態は ✅ に、廃止した機能は行を消さずに「廃止（理由・Issue 番号）」として残す。
4. 機能 ID（例: `V-03`）は **再利用しない**。Issue・PR・テストから参照するための恒久的な目印。
5. 来訪者視点の変更は従来どおり `docs/changelog-unreleased/` にも書く（こちらはリリースノート用）。
6. 四半期に一度、重要度と状態の棚卸しをする（ロードマップの見直しと同時）。

### 機能 ID の接頭辞

- `V-xx` 来訪者（Visitor） / `S-xx` 出店者（Shop） / `A-xx` 管理者（Admin） / `M-xx` モデレーター（Moderator）
