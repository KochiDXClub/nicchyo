# 出店者（Shop / `vendor`）の機能要件

対象: 日曜市の出店者。**スマホで、IT に不慣れでも、店先で短時間に操作できる**ことが大前提。
自店舗（`vendorId` に紐づく店舗）のデータだけを編集できる。

> 重要度の基準は [README.md](./README.md) を参照。画面の使い方の単一情報源は `lib/vendor/helpGuide.ts`（#767 のマージで `lib/vendor/helpFaq.ts` に置き換わる予定。マージ時に直す）。

## S-01 近況を出す【S】

**要件**
- 写真1枚（必須）＋ひとこと（任意）で、今日のおすすめ・残り数量・出店場所の変更を発信できる。
- 掲載期間を選べる（日曜まで／1時間／時間指定）。期間が過ぎたら自動で非表示。
- 投稿は `/story` とマップのショップバナー「今日のお知らせ」の両方に出る。

**重要な要素**
| 要素 | 重要度 | 理由 |
|---|---|---|
| 数タップで完了する（入力項目を増やさない） | **S** | 店先で使われる。面倒だと使われなくなる |
| 期限切れの自動非表示 | **S** | 古い情報（売り切れ）が来訪者を誤誘導する |
| 自店舗以外に投稿できない（認可） | **S** | なりすまし・誤公開の防止 |
| 画像の自動軽量化 | A | 来訪者側の表示速度 |
| 不適切投稿の報告・非公開化との連動 | A | A-04 / M-01 |

## S-02 店舗情報の更新【S】

**要件**: 店名・紹介文・商品・写真・SNS・決済方法を更新できる。変更は即座にマップ・検索・ショップバナーへ反映。
**重要な要素**: 自店舗以外を編集できない **S** / 誤編集からの復元（監査ログ）A / 商品一覧の入力しやすさ A / 必須項目の入力進捗が分かる B。

## S-03 出店予定日・お休み登録【S】

**要件**: 出店する日曜／お休みする日曜を登録。来訪者のカレンダー・店舗情報に反映。
**重要な要素**: 来訪者が「今日その店がやっているか」を判断できる **S** / 登録の簡単さ A。

## S-04 出店者トップとにちよさん相談【A】

**要件**: 最初に開く画面。次にやることが分かる（近況・店舗情報）。にちよさんと話して、お客さんに伝えたいこと（混む時間・おすすめの食べ方など）を残せる。使い方も質問できる。
**重要な要素**: 迷わず次の操作へ進める **S** / 会話から得た内容は **出店者が確認・訂正できる**（S-07）**S**。

## S-05 運営・市役所との連絡【A】

**要件**: 運営からのお知らせを読む（既読管理）。質問・相談を送り、返信を受け取る。
**重要な要素**: お知らせの見落とし防止（未読表示）**S** / 問い合わせがスレッドで追える A / 管理者側（A-03）に確実に届く **S**。

## S-06 投稿履歴・出し直し【A】

**要件**: 過去の投稿を見返し、そのまま／写真・ひとことを直して出し直せる。
**重要な要素**: 出し直しが S-01 と同じ手軽さ A。

## S-07 にちよさんの覚えごと【A】

**要件**: AIが相談から覚えた店舗ナレッジを一覧し、直す・忘れさせる。
**重要な要素**: **出店者が内容を完全にコントロールできる**（AIが誤情報を来訪者に伝えないため）**S** / 削除が即時にRAGへ反映 A。

## S-08 〜 S-11（要点のみ）

- **S-08 お店の分析**【B】: 閲覧回数・お客さんの質問傾向（数字は記録があるぶんだけ表示される）。データは「管理」でなく改善のために見せる（ROADMAP）。
- **S-09 使い方ガイド**【B】: 画面の変更時は `helpGuide.ts` を必ず更新（にちよさんの回答の根拠でもある）A。#767 で「よくある質問」（`helpFaq.ts`）に変わる予定。
- **S-10 アカウント設定**【A】: 1 店舗に複数のアカウント（代表者 1 人＋メンバー）が入れる。ログインは Google 認証のみ（メール・パスワードの編集は無い）。
  - メンバーごとに操作権限を付け外しできる（店舗情報の編集 / 近況 / にちよさんの覚えごと / 運営との連絡 / 分析 / 操作ログの閲覧 / メンバーの管理）。代表者は常に全権限。
  - **招待リンク**: 有効期限 7 日、1 本で入れる人数は 1〜5 人（作るときに決める）、入った人の権限も作るときに決める。URL は作った直後の 1 回だけ表示（サーバーにはハッシュだけ保存）。
  - **メンバーの管理**ができるのは代表者と `members_manage` を持つメンバー（副代表）。副代表でも、`members_manage` の付け外し・副代表どうしの変更・自分が持たない権限の付与は**代表者だけ**。自分自身の権限は自分では変えられない。
  - **代表者の引き継ぎ**: 今の代表者が、同じ店舗のメンバーに引き継ぐ。もとの代表者は全権限の副代表として残る。代表者は先に引き継がないと店舗を抜けられない。
  - **操作ログ**: メンバーの参加・抜ける・外す・権限変更・招待の作成/取り消し・引き継ぎ・QR の発行/解除を記録（個人情報は入れない・追記専用）。見られるのは代表者と操作ログの権限があるメンバー。運営は管理画面から全店舗。
  - 重要な要素: 権限の判定は DB（RLS・`has_shop_permission`）と API の両方で守る **S** / メンバーを外したら即座に権限を失う **S** / 権限のない人に導線を出さない A。
- **S-10b 退会とデータ削除**【A】: 取り消せない操作なので、消えるもの・残るものを先に説明し、「退会する」の入力を確かめてから実行する（`DELETE /api/vendor/account/delete`）。
  - **消すもの**: ログインアカウント／代表者として登録した氏名と公開設定（`vendor_owner_profiles`）／操作ログに載った自分の名前（「退会したメンバーに関する記録」になる）。
  - **残すもの**: お店の掲載情報（店名・商品・写真・近況。公開情報のため）。消したいときは、退会の前に運営へ連絡。運営・市役所とのやりとりの内容は残る（送った人の名前は残らない）。
  - 代表者は、ほかにメンバーがいる間は退会できない（先に引き継ぎ）。メンバーが自分だけなら、出ている招待リンクを取り消し、お店はアカウントなしに戻る（運営が QR を出し直す）。
  - 途中で失敗してもやり直せる順序（匿名化 → 氏名の削除・招待の取り消し → アカウントの削除）。
- **S-12 招待リンク・QRコードで参加**【A】: `/join/<トークン>`（招待）・`/claim/<トークン>`（運営が配る QR）。ログイン前でも「どのお店か」を見せ、Google でログイン → 参加。QR は、店舗にまだ代表者がいないときだけ、最初にスキャンした人が代表者になる（運営が再発行・解除できる）。トークンの URL は検索に載せず、外部へ Referer を渡さない。
- **S-11 初回セットアップ**【B】: 店舗名・出店日・写真・初投稿の4項目。

## 出店者向けの非機能要件

| 要件 | 重要度 |
|---|---|
| 自店舗のデータのみ読み書き可（RLS＋API認可の二重） | **S** |
| スマホで片手操作できる大きさ・分かりやすい言葉 | **S** |
| 画面文言のやさしさ（専門用語を使わない） | A |
| 操作の取り消し・やり直しができる | A |
| 出店申請〜アカウント発行の導線 | ❓ 要確認 |
