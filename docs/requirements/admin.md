# 管理者（Admin）・モデレーター（Moderator）の機能要件

対象: 運営（高知市・高専などの運営チーム）。
ロール: `admin`（最上位）／`moderator`（投稿・通報の確認担当）。

> 管理画面の項目の単一情報源は `lib/admin/adminNav.ts`。**現状 `/admin/*` に入れるのは admin のみ**（layout のガードが `isAdmin()`）。moderator は `/moderator` を使う。moderator への `/admin/*` の部分開放は将来対応。
> 重要度の基準は [README.md](./README.md) を参照。

## A-01 日曜市カレンダー運用【S】

**要件**: 開催／荒天中止／特別開催のステータスを切り替え、出店予定・イベントを入稿する。変更は来訪者のカレンダーとマップ・近況の告知バーへ反映。
**重要な要素**: **中止の即時反映 S**（来訪者が現地へ向かう前に伝わる）/ 切替ミスの防止（確認ダイアログ）A / 操作の監査ログ A。

## A-02 店舗データ管理【S】

**要件**: 店舗（1〜300）の確認・編集・一括操作。
**重要な要素**: 店舗コードの整合（`normalizeShopCodeToId`）**S** / 一括操作の取り消し・確認 A / 非公開化の即時反映 A。
**掲載許可**: 店舗ごとに許可（未取得／許可済み／断られた）・写真の使用許可・許可日・メモを記録し、**許可済みの店舗だけを来訪者に出す**（DB の RLS。出店者のアカウントとは独立）**S**。許可の記録は運営だけが変更できる（出店者本人は変えられない）。一覧と詳細（`/admin/shops/[id]`）で確認できる。仕組みは [VENDOR_ACCOUNTS.md](../VENDOR_ACCOUNTS.md)。

## A-03 受信トレイ・問い合わせ【S】

**要件**: 出店申請・通報・問い合わせの通知を一箇所で確認し、出店者への返信・お知らせ送信ができる。未対応件数をバッジ表示。
**重要な要素**: **見落とさない（未対応バッジ）S** / 出店者向けお知らせの宛先ミス防止 A。

## A-04 投稿の確認・非公開化【S】

**要件**: 出店者の投稿を確認し、不適切なものを非公開にする。
**重要な要素**: 非公開が来訪者側へ即時反映 **S** / 非公開の理由が残る A。

## A-06 ユーザー・ロール管理【S】

**要件**: アカウント検索・ロール変更・一括操作。
**重要な要素**: **ロール変更は admin のみ・監査ログ必須 S** / 最後の admin を失わない A / 出店者と店舗の紐づけの正確さ **S**。

## A-05 / A-07 〜 A-16（要点のみ）

- **A-05 通報**【A】: 来訪者の通報を確認・対応状況管理（未対応／確認中／対応済）。
- **A-07 マップ編集**【A】: 建物・店舗配置、動かせる範囲。座標の基準は `config/roadConfig.ts`。**誤編集が来訪者のマップを壊すため、スナップショット（復元）が必須 S**。
- **A-08 スポット**【A】: トイレ等の位置。来訪者のおでかけサポート（V-07）の正確さに直結。
- **A-09 カテゴリ**【B】: 検索・マップのジャンル。削除時に店舗への影響を確認。
- **A-10 分析**【B】: 訪問者・人気店舗。個人を特定しない集計のみ **S**（ROADMAP「統制のためでなく改善のため」）。
- **A-11 設定**【A】: 公開範囲・機能フラグ・通知メール。誤設定で全体に影響するため変更前確認 A。
- **A-12 AI設定**【A】: プロンプト・モデル・会話設定。**変更履歴と戻せること S**（回答品質が全来訪者に影響）。
- **A-13 監査ログ**【A】: 管理操作の履歴。**書き込み漏れがない S**（認可・変更系 API は必ず記録）。
- **A-14 週次レポート**【B】: セキュリティ状況の定期確認。
- **A-15 計測・健康診断**【C】: 開発者向け。運用には不要。
- **A-16 危険な操作**【A】: 通常画面と分離し、実行前確認を必須とする。

## M-01 / M-02 モデレーター

**要件**: 通報・投稿を確認し、対応する。出店者データ・ユーザー・設定は変更できない。
**重要な要素**: **権限の最小化 S**（読み取りと対応のみ）/ 対応履歴が残る A / `/admin/*` を開放する際は layout の認可を先に見直す（adminNav.ts の注記）S。

## 管理者向けの非機能要件

| 要件 | 重要度 |
|---|---|
| すべての管理 API が API 側でも認可（画面の非表示に頼らない） | **S** |
| RLS ポリシーの網羅（新テーブル追加時は security-reviewer を通す） | **S** |
| 変更系操作の監査ログ | **S** |
| 管理画面は PC 中心でも、緊急操作（中止の切替）はスマホで可能 | A |
| 個人情報（メール・電話）の表示最小化 | A |

## A-17 店舗のQRコード・店舗の操作ログ【S】

**要件**: 店舗データを先に入れ（アカウントなし）、出店者へ配る QR コードで Google アカウントを代表者として紐づける。運営は QR を発行（再発行）し、紐づけを解除し、店舗ごとの操作ログを見られる。
- QR は店舗ごとに有効なものが 1 つ（再発行で前のものは無効）。代表者がいる店舗には発行できない。最大 300 店を一括発行でき、印刷用のシートを出す。URL（QR の中身）は発行した画面でしか見られない（サーバーにはハッシュだけ）。
- **紐づけの解除**: メンバー全員を外し、出ている招待リンク・QR を取り消して、店舗をアカウントなしに戻す。店舗の掲載情報（商品・写真・投稿）は残る。実行前に、外れる人数を確かめる。
- 操作（発行・解除）は `admin_audit_logs`（運営向け）と店舗の操作ログ（出店者向け・「運営が…」と表示）の両方に残す。

**重要な要素**: QR が推測・流出で乗っ取りに使われない（ハッシュのみ保存・使い切り・再発行で無効化）**S** / 解除の取り違えを防ぐ確認 **S** / 店舗の操作ログを運営が全店舗分読める A。
