# リポジトリセキュリティレビュー（2026-11-04）

対象: KochiDXClub/nicchyo の develop `9d19667cb089e6ae24c6c20a144f971a0ffc40e9`。
ソース・DBマイグレーション・依存ロック・CI設定を調査した。実環境への侵入試験や本番DB・Storageの読み書きは行っていない。

## 結果と深刻度

| ID | 深刻度 | 問題 | 状態 |
|---|---|---|---|
| SEC-01 | 高（機密性） | 出店者から運営への非公開の連絡画像が公開Storageに保存される | 新規保存・表示を修正。**既存画像の移行が完了するまで既存公開URLの問題は未解消** |
| SEC-02 | 中（完全性・リソース消費） | 閲覧ログの直接INSERTでAPIの入力検証・レート制限を迂回できる | APIの書き込みをservice roleへ移し、DBの直接INSERTを閉じるマイグレーションを追加 |
| DEP-01 | 中（開発ツール依存、監査ツールの分類） | minimatch の globparts amplification / DoS（GHSA-g3hv-75wg-m249） | 開発依存に残存。下記に到達条件と未適用理由を記載 |

「高」は未認証の第三者が非公開情報を取得できる場合、「中」は公開情報の集計改ざん・負荷増大、または実行条件を要する開発ツールの問題として分類した。侵害が実際に起きたという判断ではない。

### SEC-01: 公開バケットの連絡添付画像

- 保存元: `app/vendor/_services/inquiriesService.ts` が `vendor-images/{vendorId}/inquiries/{timestamp}.webp` にアップロードし、公開URLを保存していた。
- DB: `20260309005000_create_vendor_images_bucket.sql` のバケットは `public=true`。`public can view vendor images` はバケット内を公開SELECTできるため、オブジェクトの列挙も可能だった。
- スレッド本文は認証・店舗所属で守られるが、画像を取得する経路はその認可を通らない。公開バケットのダウンロードはRLSのSELECT制限だけでは閉じない。
- 影響: 連絡に添付された写真・スクリーンショットの情報が第三者から取得され得る。対象画像の実在や内容、本番へのマイグレーション適用状況は未確認。

修正:

1. 専用の非公開バケット `vendor-inquiry-images` に保存する。DBには署名を含まない `inquiry-image:` 参照だけを保存する。
2. スレッドの閲覧認可後に、店舗IDと保存パスの対応を検証し、5分の署名URLを返す。他店舗・旧公開URL・外部URLは署名しない。
3. StorageのRLSで、当該店舗の `inquiries` 権限を持つメンバーと運営の読み取りだけを許す。アップロード・削除も所属店舗と権限で制限する。
4. 旧公開フォルダへの新規アップロード・更新・列挙を閉じる。**旧公開URLのダウンロード停止には、後述の画像移行と公開コピー削除が必要**。
5. 署名を返すAPIは `private, no-store`。添付の Next/Image は `unoptimized` とし、公開の画像最適化キャッシュに非公開画像を残さない。新規画像のStorageキャッシュも0秒にする。

### SEC-02: 閲覧ログの直接書き込み

- `web_page_analytics` の `public insert page analytics` は `WITH CHECK (true)`。anon/authenticated のINSERT権限も残っていた。
- 公開クライアントキーを使ってPostgRESTへ直接書き込めるため、`/api/analytics/page-visit` の同一オリジン確認・レート制限・パス検証・サーバー側ロール判定を迂回できる。
- 影響: 任意の日付・ページ・滞在時間・ロールを含む偽の閲覧記録、統計の汚染、大量書き込みによる保管コスト増加。
- 修正: Cookieクライアントはユーザーの検証だけに使い、検証済みのログはservice roleで保存する。直接INSERTポリシーとanon/authenticatedの権限を削除する。管理者側の既存SELECTは維持する。

### DEP-01: 開発依存の監査結果

- `npm audit --omit=dev --json`: 本番依存の既知脆弱性は0件。
- `npm audit --json`: minimatchの1つのアドバイザリがESLint/Vitest等へ伝播し、中のパッケージ項目が20件。独立した20種類の脆弱性という意味ではない。
- Advisory: https://github.com/advisories/GHSA-g3hv-75wg-m249 。修正版は11.0.1以上と報告されるが、現在の依存経路に互換性を保つ修正をauditは提示していない。
- 本番HTTP入力からminimatchのglob指定へ届く経路は今回の調査では見つからなかった。開発/CIで外部から渡される巨大なglobを評価する場合に注意が必要。
- 強制的なメジャー版overrideはESLint/VitestのAPI互換性を崩し得るためこのPRでは実施しない。上流依存の互換更新を追跡する。

## 既存画像を保護するリリース手順（ドラフトの解除前に確認）

1. Preview/開発DBで `20261104100000_private_inquiry_images_and_analytics_writes.sql` と新コードを検証する。新バケットがprivateであることを確認する。旧コードだけの期間は、添付アップロードと閲覧ログの旧直接INSERTが拒否されるため、アプリとSQLは同一リリースとして扱う。
2. ストレージと `vendor_inquiries` のバックアップ/復旧方法を確認する。本番の適用は通常のリリース承認で行う。このPR作業では適用しない。
3. 既存のサーバー用環境変数 `NEXT_PUBLIC_SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` を安全な実行環境で設定し、`node scripts/migrate-inquiry-images.mjs` を実行する。既定はdry-runで、対象数だけを出力する。鍵や画像内容をログへ出さない。
4. 対象プロジェクトを確認して `node scripts/migrate-inquiry-images.mjs --apply` を実行する。公開コピーをダウンロードし、非公開側へコピー、SHA-256を照合、DB参照を更新してから、公開コピーを削除する。孤立した添付画像も非公開側に保管する。通常の店舗写真は対象にしない。
5. エラー時は停止する。コピー・DB更新に失敗した場合は公開コピーを削除しない。途中まで完了した場合は再実行できる。想定外のファイル名・形式は自動削除せず個別に確認する。
6. dry-runを再実行して対象0件を確認する。`vendor_inquiries.image_url` に旧公開URLが残っていないことも確認する。実Storageの旧公開URLが取得できなくなったこと、新しい画像を未ログイン/他店舗/権限なしメンバーが取得できないこと、許可された本人と運営には表示されることを確認する。
7. Storage/CDN・Next.jsの旧画像最適化キャッシュ・ブラウザに既に残ったコピーは、オブジェクト削除だけで即時に全て消えるとは限らない。旧URLの実際の応答とキャッシュ失効を確認し、必要ならプロバイダー側の無効化を行う。既に第三者が取得したコピーを取り戻すことはできない。

署名URLは有効期間中は共有可能なBearer URLであり、期限切れ後は画面を開き直して再取得する。実データの移行・旧URLの失効確認が終わるまでSEC-01を「対応完了」と扱わない。

## 回帰検証

- 認可されないユーザー・別店舗では署名処理を呼ばず、認可後のレスポンスは共有キャッシュに残さないAPIテスト。
- パス偽装・他店舗・旧公開URLの拒否、短期署名、署名失敗時のfail-closed。
- 画像移行のdry-run、コピー破損、DB更新失敗、削除順序のテスト。
- 閲覧ログのservice role保存と、未設定時に公開クライアントへ戻さないテスト。
- PostgreSQL 17の隔離した最小スキーマで実際の既存権限ヘルパーと新マイグレーションを適用し、anon/本人/他店舗/権限なしメンバー/運営でSQL回帰検証。全マイグレーション後の検証はCIのMigrations Checkにも追加。
- 本番のDB/Storage設定・実画像・キャッシュ状態は未検証。上記リリース手順で確認する。
