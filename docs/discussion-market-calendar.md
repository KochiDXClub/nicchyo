# 💡 提案：「ニュース」を作り直し、日曜市の開催情報を発信する

## 背景：ニュース機能と近況機能の関係を整理したい

現状、リアルタイムな情報発信に関わる機能が2つあります。

- **近況（`/story`）**：出店者が写真付きで投稿。鮮度順に並び、古いものは色あせる。ハートリアクションあり。マップの店舗バナーからも直接開ける。**実装済み・DB連携済み**。
- **ニュース（`/news`）**：`newsItems` がハードコードのダミー配列。カテゴリは「お知らせ / アップデート / メンテナンス / イベント」。メニューシートの2列グリッドの3番目にあり、導線としてはほぼ機能していない。**中身は未実装**。

「ニュース」は機能が弱いというより、まだ何も無い状態です。作り直す前提で設計できます。

そのうえで目指したいのは、**「何日にイベントがある」「この日は休み」といった日曜市そのものの情報を、運営元である高知市役所が「これは良い」と言うレベルでリアルタイムに発信でき、来訪者が受け取りやすい形で届く**ことです。

## 課題1：今の「ニュース」は異質な2つが混ざっている

「アップデート」「メンテナンス」は**アプリの都合**であり、来訪者にとっての価値はほぼありません。一方「イベント」「休み」は**日曜市そのものの情報**です。この2つが同じリストに並んでいる限り、どれだけ作り込んでも「見に行く理由のないページ」のままです。

→ アプリの更新情報は `/about` 配下などに隔離し、このページからは追い出します。

## 課題2：すみわけの軸をどこに置くか

「運営が出すか / 出店者が出すか」で切ると必ず被ります。**時制**で切ると綺麗に割れます。

| | 近況 | 日曜市カレンダー（旧ニュース） |
|---|---|---|
| 時制 | **いま〜さっき** | **これから（日付が決まっている）** |
| 来訪者の問い | 「今日行ったら何がある？」 | 「いつ行けばいい？」 |
| 使う場面 | 市の最中・直前 | 訪問を決める前 |
| 主役 | 写真 | 日付 |
| 寿命 | 数時間〜1か月で色あせて消える | 当日まで残り、当日を過ぎたら消える |
| 発信者 | 出店者 | 運営・高知市役所 |
| UI | ストーリー／グリッド | 日付順リスト |

この線引きなら「8/17にイベント」は後者、「今日は文旦が入荷しました」は前者で、境界で悩むケースがほとんど出ません。

### 名前について

「ニュース」は**過去の報道**を連想させるため、未来の予定を置く箱としては名前が嘘になります。中身が日付主体になるなら名前も日付を名乗るべきで、**「日曜市カレンダー」**（または「開催情報」）を提案します。市役所側も何を入稿すればよいか一発で分かります。

### 出店者個人の休みはこの機能の対象外

出店者の休業日は各ショップバナー側で報告する想定です。データとしても `vendors.closed_dates`（date配列、`app/vendor/_services/closedDatesService.ts`）が既にあります。

→ **カレンダーは市全体のことだけを持てばよく**、店舗単位の休業は責務から外せます。

## 提案：カレンダーを独立ページにせず、近況ページの下に置く

メニューの奥に埋めると誰も見ません。一方で、来訪者が**リアルタイムな情報を求めて最初に開くのは近況ページ**のはずで、その人は出店者の投稿と運営のイベント情報の両方に興味があるはずです。

そこで、**公式（運営）の発信を近況ページの「出店者投稿の下」に独立セクションとして置く**構成にします。

### なぜフィードに混ぜず「下に別セクション」なのか

運営の投稿を出店者投稿と同じグリッドに混ぜる案も検討しましたが、別セクションにすることで設計上の問題が3つとも構造的に消えます。

1. **退色ロジックの破綻を避けられる**
   近況の鮮度表現（`getStoryAgeBucket` / `STORY_AGE_IMAGE_CLASS`）は `created_at` で色あせさせる仕組みです。未来のイベントを投稿すると `created_at` は「今」なので、常に「今週」扱いで最上位に鮮やかに居座り、イベントが終わっても色あせません。時制が逆のものを同じ並びに入れると必ず破綻します。別セクションなら退色ロジックの外なので、「いま」も「予定」も同じ場所に置けます。

2. **出店者の投稿が埋もれない**
   運営は毎日投稿できて、出店者は週1です。混ぜると放置すれば近況＝運営の広報板になり、出店者の投稿が埋もれて余計に投稿しなくなります（悪循環）。「Featured枠は出店者優先」のようなルールで抑える設計はいつか破られますが、セクションを分ければ構造的に起きません。

3. **公式バッジが必須ではなくなる**
   セクション見出しが区別になるため、「公式」表示は必須要件から「あってもよい」に格下げできます。

さらに、`/api/stories` も `StoryGridClient` の鮮度ロジックも**一切触らずに済みます**。

### 代償と、その回収方法

代償は「ページを開いた瞬間の密度が出店者投稿だけで決まる」ことです。過疎のときスカスカのグリッドが最初に来ます。これは例外2つで回収します。

1. **開催ステータスの1行バーは最上部に置く**
   「今週開催 / 荒天中止 / 特別開催」は予定ではなく「いま」の情報であり、中止の連絡がページ下部にあっては意味がありません。カレンダー本体は下に置きつつ、ステータスだけは細い1行で最上部に固定します。マップページにも同じバーを常設します。

2. **今週の出店者投稿が0件のときだけ、公式を上に出す**
   現在の `EmptyState`（「まだ投稿がありません／次の日曜市は◯月◯日」）を公式セクションで置き換えます。条件分岐1つで済みます。

### ページ構成案

```
┌ 今週の日曜市：開催 / 荒天中止          ← 細い1行・最上部（例外1）
├ 近況（ヒーロー見出し）
├ 今週の投稿  [FeaturedStoryPreview]
├ 今週 / 1週間前 / 1か月前  グリッド
│      ※ 投稿0件のときは、ここに公式セクションが繰り上がる（例外2）
├ ──────────────────────────
├ これからの日曜市                        ← market_events 直近3件
│      8/17（日）  朝市まつり
│      8/24（日）  文旦シーズン開始
│      すべて見る →
└ フッター
```

メニューの「ニュース」項目は `/calendar` にリネームして残します（市役所がURLで見せられる・共有できることに価値があるため）。ただし**主導線は近況ページ下部の「すべて見る」**で、メニューは補助入口に降格します。

## 市役所に対して価値になるのは「機能」ではなく「役割」

市役所が最も喜ぶのは、おそらくイベント告知よりも**当日の開催可否**です。雨天中止・年末年始・臨時休市の連絡は、現状おそらく電話と貼り紙で回っています。ここを押さえると nicchyo は「便利アプリ」から**公式の一次情報チャネル**になります。提案するならセットで：

1. 運営／市役所ロールが「今週の開催ステータス」をワンタップで更新できる
2. それがマップと近況ページの最上部に常設1行で出る ← **これが本体**
3. 何人に届いたかが数字で出る（`app/api/analytics/` が既にある）

## 既存資産：思ったより揃っている

- **`market_events` テーブルは既に存在します**（`supabase/migrations/20260630000003_create_market_events.sql`）
  `title` / `description` / `event_date` / `start_time` / `end_time` / `location` / `is_published` / `created_by` を持ち、RLS も「公開分（`is_published = true`）は誰でも読める・書き込みは admin のみ」で設定済み。`anon` / `authenticated` への `GRANT SELECT` もあります。
- **管理APIも既にあります**（`app/api/admin/events/route.ts`, `app/api/admin/events/[id]/route.ts`）
- **公開側のUIだけが無い状態**です。
- **`vendors.closed_dates` も既存**（`20260718182137_add_closed_dates_to_vendors.sql`）

## 進め方

### フェーズ1：`market_events` を公開する（新規テーブル不要）

- 公開読み取りAPI 1本
- 近況ページ下部「これからの日曜市」セクション
- 開催ステータス1行バー（マップ＋近況ページ）
- `/calendar` 詳細ページ（旧 `/news` をリネーム、アプリ更新情報は退避）

`vendor_contents` は変更なし、`/api/stories` は無改造。既存テーブルと既存の管理APIに乗るため、実装量のわりに見栄えが立ちます。**フェーズ1だけで市役所に見せられる状態**になります。

### フェーズ2：運営の「いま」投稿をどうするか判断する

「今日の会場の様子」「〇〇が入荷しました」のような運営発の近況を、出店者投稿と同じフィードに混ぜるかどうか。近況ページの投稿が過疎になる懸念への対策として有効ですが、フェーズ1の運用実績を見てから決めれば十分です。

混ぜる場合の実装案：

- **A案**：`vendor_contents` に `author_type ('vendor' | 'official')` を追加し `vendor_id` を nullable 化。RLS で official は admin のみ INSERT。ハート（`content_reactions`）・ビューア・退色がそのまま流用できる。
- **B案（検証用）**：「nicchyo運営」という vendor レコードを1件作るだけ。マイグレーション不要で即日試せる。

## 関連：旬タグ提案との位置づけ

`docs/discussion-seasonal-tag.md` の旬タグも同じ空間の話です。3つ並べると軸が揃います。

- **近況** = いま（時間・出店者発）
- **カレンダー** = いつ（日付・運営／市役所発）
- **旬タグ** = なに（モノ・運営企画 × 出店者ワンタップ）

被っていません。旬タグの「旬の1週間前に通知」も、カレンダー側に「文旦シーズン開始 8/24〜」として置けば自然につながります。

## 議論したいこと

- ページ名は「日曜市カレンダー」でよいか（「開催情報」なども候補）
- 開催ステータスの選択肢をどこまで持つか（開催 / 荒天中止 / 特別開催 / 臨時休市 …）
- 開催ステータスを `market_events` に持たせるか、別テーブル（`market_days` 等）に分けるか
- 「これからの日曜市」セクションに出す件数（3件想定）
- フェーズ2（運営の「いま」投稿）をどのタイミングで判断するか

ご意見ください 🙏
